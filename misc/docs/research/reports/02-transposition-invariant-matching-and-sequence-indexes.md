# Transposition-invariant chord-sequence matching and sequence indexes

Research report, 2026-11-08. Scope: how to represent chord sequences so that "Am E F" finds "Dm A Bb", which matching parameters the literature and existing tools support, and which index structure fits ~17M chord tokens now and ~100M later, including an in-browser path. Harmony theory itself is out of scope (covered in-house).

## Summary and recommendation

The best-evidenced representation is the simplest: store chords as **absolute (root, quality-level) tokens and run the query in all 12 transpositions**. Hanna, Robine and Rocher tested exactly this against key-relative and interval-relative representations on a Real Book retrieval task: absolute-plus-transposition scored 0.840 first-tier against 0.712-0.722 for key-relative and 0.615 for plain absolute, and they attribute the key-relative loss to wrong key annotations and in-song key changes [1]. Chord Genome's "All Keys" filter is the same idea in a product [2]. Root-interval sequences (deltas) are index-friendly and need one query instead of 12, but the same group found relative representations "less accurate when applied with alignment algorithms" [1], and they lose the first chord's identity, so keep them as a derived view (for counting progression classes), not as the primary key.

Quality should be stored as a **ladder of levels**, mirroring mir_eval's vocabularies (root, majmin/thirds, triads, tetrads, exact) [3]; the user's "triad-only vs exact-extension" switch picks the level, and "E(7)" becomes two alternatives at the exact level or one token at the triad level.

For the index, the **no-new-dependency baseline (SQLite FTS5 phrase queries over a tokenised chord string, 12 OR'd phrases, a sentinel token at every section boundary) is good enough for v1** at 135K songs; it lives in the same SQLite file the existing index uses, and NEAR() gives gapped matching for free [4]. The **v2 index is a suffix array over a uint8/uint16 token stream** (pydivsufsort, MIT, accepts numpy integer arrays [5]): 12 binary searches answer an exact query in microseconds, occurrence counts and song listing fall out of the matched range, and the whole structure is ~5 bytes per token (estimate: ~85 MB at 17M tokens, ~500 MB at 100M). In the browser, at 135K songs a **packed byte array plus a linear scan** is likely enough (estimate: ~17 MB raw, a few MB compressed; tens of milliseconds per query with typed arrays); FTS5 is also available there because the canonical SQLite WASM build includes FTS5 [6]; a WASM FM-index is the path for 800K songs, with no mature off-the-shelf JS library found.

Ranking: popularity first, then in-song occurrence count and coverage (which the suffix array and positional index give for free); FTS5's bm25() is wrong for a 60-symbol alphabet and should not be used.

## 1. Representations for transposition invariance

The three representations in the literature, compared on what the brief asks for:

| Representation | Transposition | Modulation inside a song | First-chord ambiguity | Quality | Index-friendliness | Verdict |
|---|---|---|---|---|---|---|
| Absolute tokens, query transposed 12 times | 12 queries (trivial on an index) | Handled: a match is local, no global key needed | None | Any level | Best: plain tokens, any text index | **Use first** [1,2] |
| Root-interval deltas (semitones mod 12 between consecutive roots) plus qualities | 1 query | Handled (local) | The first chord's root is lost; a 3-chord query becomes 2 deltas, so "Am E F" and "Bm F# G" and any other transposition collapse together (desired), but so do fragments that merely share motion | Attached per token | Good: 12x smaller vocabulary, one query | Derived view for aggregation (progression classes, idiom counting [7]); Hanna et al. found it less accurate for alignment [1] |
| Key-relative (scale degree / roman numeral after key estimation) | 1 query | Fails on modulation unless the key is tracked per segment | None | Roman numerals carry quality | Good, and it is what Hooktheory indexes because its tabs are human-annotated with key [8] | Later option, only with a confidence score: wrong key estimates hurt retrieval in [1]; TPSD also "requires the key" as input [9] |
| Pitch-class-set / chroma (12-bit vector per chord) | 12 rotations | Local | None | Collapses quality into pitch content (mir_eval's "mirex" vocabulary: 3 shared pitch classes count as equal [3]) | Poor for exact search, fine for similarity | Not for v1 |
| TPSD (de Haas, Veltkamp, Wiering): step function of Lerdahl TPS distance from each chord to the key's tonic triad, compared under cyclic shift | Key-invariant by construction | Needs the key as input; authors say modulation info "is rarely present" in chord data | None | Uses TPS chord distance | None: O(nm log(n+m)) pairwise, no index; a whole-song similarity measure, not pattern search | Study only [9] |
| Chord Sequence Alignment (Hanna et al.): Smith-Waterman local alignment with substitution scores on root/bass (fifths, consonance) and mode, transposition handled inside the alignment | Inside the algorithm | Local alignment tolerates it | None | Mode as a small bonus/penalty | None: pairwise O(nm) | Use as the **re-ranker** for approximate matches on candidates an index found [1] |

Two further facts from the papers that bear on design. Hanna et al. report that comparing chord type is "too accurate for retrieval purposes and leads to poor results", so root-level matching with mode as a soft bonus beat exact-quality matching for similar-song retrieval [1]; for the user's exact-progression search this argues for defaulting to the triad level and offering exact as the stricter switch. De Haas et al. later compared TPSD and the alignment system (CSAS) and report CSAS won 4 of 6 tasks, with TPSD having the better quality-to-runtime ratio [10,11]; the same group's HarmTrace used functional-harmony annotations to improve alignment [11]. Nothing in this literature indexes a corpus; every system scores pairs.

Key estimation from chord symbols, if ever wanted for the key-relative view: Krumhansl-Schmuckler profile correlation is the standard, its weaknesses (confusing related keys, modulation) are documented [12], and music21's `romanNumeralFromChord(chord, key)` will label any chord relative to any key, producing awkward labels for out-of-key chords [13]. No source applying profile correlation directly to chord-symbol sequences was found; the chord-to-pitch-class weighting would be a design choice.

## 2. Matching parameters

How each parameter in the brief maps onto an index, with the literature or tool that does it:

- **Optional tokens** ("E(7)"): expand to alternatives at query time; on a suffix array each alternative is one more binary search, on FTS5 it is one more phrase in an OR. At the triad level the question disappears because E and E7 are the same token.
- **Gaps and skips**: FTS5 `NEAR(p1 p2 ..., N)` matches when at most N tokens separate the phrases; its own examples show order is not required [4], so ordered gapped matching needs a post-filter on positions. The general technique is filter-and-verify: find candidates from exact q-grams, then verify with an alignment (Navarro's survey of approximate string matching [14]; gapped q-grams filter "orders of magnitude" better than contiguous ones for some error levels [15]). For chord search the verify step is the Hanna alignment [1].
- **Wildcards** ("Am ? F"): a wildcard splits the pattern into pieces; on a suffix array match the pieces and intersect positions with the required offsets; on FTS5 use `NEAR("Am" "F", 1)` then check positions. Chordonomicon-style section markers must not be counted as tokens in the gap.
- **Repeats** ("C C C G" vs "C G"): run-length compress consecutive identical tokens at index time and store run lengths as a payload; query both forms. Mauch et al. note repeated chords are common in pop (Beatles) and rare in the Real Book, so the switch matters by genre [7].
- **Slash chords / inversions**: index by root with the bass as payload; Hanna et al. tested root-based and bass-based substitution scores and found them close (0.840 vs 0.808 first tier) with a combined root/bass fifths score at 0.850 [1]. Chord Genome ignores inversions entirely [16]. Offer "match by root" as the default and "match by bass" as a second token stream only if asked.
- **Quality loosening**: the mir_eval ladder is the vocabulary to borrow: root; majmin (major, minor, no-chord); thirds; triads (maj, min, aug, dim, sus); tetrads (7 and 9 equivalent, 7 and maj7 not); sevenths (MIREX rules); mirex (3 shared pitch classes) [3]. Because each level is a projection of the exact token, index the exact stream and one coarse stream (triads with sus/power folded to "open", as `songleaf.harmony` already does), and derive the others by query expansion.
- **Section scope**: insert a sentinel token at each section boundary (Chordonomicon already carries `<verse_1>`, `<chorus>` markers [17]); a phrase cannot cross a sentinel, so "within one section" is the default and "across sections" is the same query over a stream with sentinels removed. With document listing at section granularity the song id is a lookup on the section's offset.
- **Cyclic matching of loops**: a 4-chord loop query means any of its 4 rotations; expand the query (4 rotations x 12 transpositions = 48 searches, still trivial on an index). The circular-pattern-matching literature solves the harder reverse problem (all rotations of a long pattern via suffix arrays of the text and its reverse) [18] and is not needed here.
- **Minimum length / cover duplicates**: filter songs below a token count; collapse duplicates on a normalised (title, artist) key or on a hash of the chord stream.

Products, for calibration: Hooktheory's TheoryTab search takes 1-4 chords in key-relative Arabic-numeral notation with an optional mode and borrowed-mode prefixes, ignores durations and, at launch, adds/sus/alterations [8]. Chord Genome searches an unordered set of 3+ chords in all 12 keys (paid) and ignores inversions [2,16]. Chordify's search is by the set of chords a player knows, over "roughly 36 million" songs, and is a set query, not a progression query (blog page returned 403 when fetched; from the search excerpt only) [19]. Ultimate Guitar's older progression search was removed according to its forum [20]. None of them documents ranking. Nothing found does ordered, transposition-invariant, gapped progression search over a public corpus, which is the gap songleaf would fill.

| q-gram / gapped q-gram index | Linear | Like n-gram index | Filter only | The point of it [15] | Normalised grams | Hand-rolled | Study |

JavaScript/WASM: no established suffix-array or FM-index package was found; an npm package "fast-suffix-array" claims a Rust/WASM suffix array and FM-index for browsers but was published days before this search and its page could not be fetched [29]. Compiling the Rust fm-index crate or sdsl-lite to WASM is the realistic route, unverified. Pure-Python suffix array construction is not viable at this scale; pydivsufsort is the Python option that needs no compiler on the user's machine.

## 4. Size and speed estimates (arithmetic shown; all are estimates)

Assumptions: 135K songs x ~125 tokens = ~17M tokens now; 800K x 125 = 100M later. Alphabet: 12 roots x 5 qualities (major, minor, dim, aug, open) + no-chord + section sentinels = ~65 symbols at the triad level (uint8); exact symbols, a few thousand distinct (uint16).

- **Token stream**: 17 MB (uint8) / 34 MB (uint16) now; 100 / 200 MB later. Chord text is highly repetitive; expect 3-5x gzip/brotli compression for download (estimate from the small alphabet and repeated progressions; not measured).
- **Suffix array**: 4 x 17M = 68 MB + 17 MB text + 0.5 MB song offsets = ~85 MB on disk, mmap-able; with LCP +68 MB. At 100M tokens: 400 + 100 MB = ~500 MB, server-only. Build: seconds now, ~1-2 minutes later at the implied divsufsort rate [21,22]. Query: 12 x 2 binary searches x ~24 comparisons = ~600 token comparisons, microseconds; song listing = unique over the matched range, proportional to hits.
- **n-gram inverted index**: a 125-token song has at most 123 3-grams, roughly 40-70 distinct after repeats (estimate). Doc-only postings: 135K x ~55 x 4 bytes = ~30 MB raw for n=3, ~40 MB for n=4; positional: 17M x (4 bytes doc + 1 byte offset) = ~85 MB raw; delta-varint coding roughly halves both. Transposition-normalised 3-gram keys: 12^2 x 5^3 = 18K possible, versus 65^3 = 275K absolute.
- **FTS5** over the same tokens with detail=full and content='' (no stored text): the posting lists carry rowid + column + offset per occurrence, so estimate 40-120 MB at 17M tokens (SQLite's email benchmark ratio was 45% of the text, but email tokens are longer and rarer than chord tokens [4]; measure). A second table for the exact level roughly doubles it. Phrase query with 12 OR'd variants: each variant intersects two or three long posting lists; expect low tens of ms (estimate), fine for the two-worker server.
- **Browser, 135K songs**: ~17 MB uint8 stream (a few MB compressed) + 0.5 MB offsets + popularity array; a 12-variant scan of 17M bytes in a Web Worker is estimated at 20-80 ms. At 800K songs (100 MB raw) the download is the limit, not the scan; that is where an FM-index (estimate 50-150 MB, still heavy) or a server round trip belongs.

## 5. The MIR literature and what an expert would add

The academic line is "harmonic similarity" and "chord sequence retrieval" for whole-song similarity: TPSD (2008) [9], the alignment system of Hanna, Robine and Rocher (2009) [1], their comparison (2010) [10], HarmTrace (2011) [11]; n-gram counting of "chord idioms" (Mauch et al., 2007) ranks progression classes by frequency across a corpus, key-independent, and is the model for a "what are the common progressions" view [7]. Evaluation uses first/second tier and top-10 on song-class retrieval over Real Book and Band-in-a-Box collections [1,9]. Recent work has moved to datasets and prediction rather than retrieval: Chordonomicon (679,807 rows on Hugging Face, licence tag cc-by-nc-4.0 on the dataset card [17]; arXiv-linked pages say CC BY 4.0 for the paper [30]; the two differ, so the dataset card governs reuse of the data), ChoCo (20K+ annotations in JAMS, 18 sources, Scientific Data 2023; data licence not found) [31]. No recent paper on indexing or "query by chord progression" at corpus scale was found; the problem is treated as solved by text indexes.

Terminology: "chord progression retrieval" or "chord sequence retrieval" (Hanna et al.), "harmonic similarity" (de Haas et al.), both under "symbolic music retrieval" / "content-based music retrieval". In string algorithms the operations are "pattern matching over a document collection" and "document listing" [23], and in search engines a "positional inverted index" / "phrase query". "Harmonic pattern retrieval" is not an established term.

What an expert would add to the brief: rank by in-song occurrence count and by coverage (tokens matched / song length), both free from a suffix-array range or positional postings; store the position of the first match so "in the chorus" and "in the first 8 bars" are filters; treat repeated sections by matching once per distinct section text and counting repeats as a weight; keep popularity in a separate, periodically refreshed array keyed by song id so refreshing it never rebuilds the sequence index, with missing popularity sorted last as the brief wants; and evaluate with a small hand-made set of known progressions (the four-chord loop, 12-bar blues, ii-V-I) at each quality level before tuning loosening defaults, since Hanna et al.'s finding that strict quality hurts retrieval [1] may or may not hold for exact-progression lookup.
